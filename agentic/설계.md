**상태: 1·2·3단계 지음(2026-10-01).** 나머지는 설계만. 아래의 성능 수는 전부 "잴 것" 이지 잰 것이 아니다.
§9 결정은 사용자가 내렸다(2026-10-01): 모델 `gemini-3.1-flash-lite` · VM 안 씀 · 정책 C 는 `sandbox/` 로 충족 · 바로 1단계.

## 0. 진단 -- 정책이 왜 "가장 기본적인 깃발조차" 못 읽었나

SE-NEXT 정책을 프롬프트로 주고 받은 답을 깃발 하나씩 증거와 맞춰 본다.

| 답에 찍힌 것 | 정책이 요구한 것 | 실제 |
|---|---|---|
| `Log: NO_LOOP_DETECTED` | F: "탐지기가 **실제로 평가했을 때만**" | 그 경로에 탐지기가 없다. 정책대로면 `UNKNOWN` 이어야 했다 |
| `Gate01 (A_TO_B: TRUE)` | G: A_TO_B 를 평가 | A 와 B 가 **무엇인지 정책 어디에도 정의돼 있지 않다.** 평가할 수 없는 것을 TRUE 로 채웠다 |
| `MCP version: 0.46.0` | A.4: 프로토콜 · SDK · 서버 버전을 **따로** | 숫자 하나뿐이다. 이 저장소 어디에도 `0.46.0` 은 없다(`grep -rw` 로 확인). 저장소의 MCP 서버는 프로토콜 `2025-06-18` 을 선언한다(`walp/mcp_server.py:24`) -- MCP 프로토콜 버전은 날짜 꼴이다 |
| `[Next]: Generate design tokens…` | H: 작업 ID · 멱등키 · NEXT_RAISED 기록 · 승인 후 디스패치 | 글자로 적힌 다음 할 일일 뿐, 사건이 아니다. 아무것도 디스패치되지 않았다 |
| 본문(산업 갤러리 → 패션) | B: 저장소를 먼저 살핀다 | 저장소와 무관한 내용. 근거 없이 지어낸 서사 |

**병은 하나다: 깃발이 모델이 낼 수 있는 토큰이었다.** 정책을 프롬프트로 주면 작은 모델은
정책을 *따르지* 않고 정책의 *출력 꼴을 흉내 낸다*. `NO_LOOP_DETECTED` 라는 낱말을 알려 준
순간 그것은 모델의 어휘가 되고, 탐지기가 없어도 찍힌다. 이 저장소가 이미 다른 자리에서 세운
규율 그대로다 -- **"모델은 제안하고 코드가 판정한다"**(`graph/README.md`), **"판정기는 모델이
아니다"**(`router/README.md` 의 `판정기` 거절), **"알려 주면 검사가 사양서가 된다"**(law/write).

그래서 이 설계의 첫째 원칙:

> **상태 깃발 · 버전 · 게이트 판정은 런타임이 원장에서 그려 낸다. 모델의 출력 스키마에는 그 칸이 없다.**
> 모델 글에 깃발 낱말이 나오면 그것은 보고가 아니라 **위조**이고, 거절한다(§5 H0).

## 1. 무엇을 하드코딩하고 무엇을 모델에 맡기나

| 하드코딩(코드 · 얼린 설정) | 모델(Gemini)이 고른다 |
|---|---|
| 모델 이름 · 폴백 없음 · 예산(바퀴·재시도·시간·호출) | 허용 목록 안에서 어떤 도구를 부를지 |
| 깃발 어휘(§5) · 종료 상태(J) · 사유 코드 | 도구 인자(스키마가 검사) |
| Gate01 의 술어 -- 작업 명세에 **실행 가능한 함수로** 박힌다 | 계획 · 중간 추론(원장에는 요약만, 생각 원문은 안 남김 -- E.6) |
| 도구 레지스트리(목록 해시 · 부작용 분류 · 권한) | RAG 질의어 |
| 루프 탐지기 · 멱등키 계산 · 사후조건 검사 | 최종 답의 글 |

얼린 설정은 `agentic/config.json` 하나이고, **실행마다 그 파일의 해시를 원장 첫 줄에 적는다.**
설정이 바뀐 실행은 다른 실행이다.

## 2. 전체 그림

```
사용자 주문
   │
   ▼
┌────────────── Controller (제어부) ──────────────┐
│ 결정적 매처(LLM 없이) -> 확실한 것만 즉시 실행     │  greedy: 의존 없는 읽기·계산은 바로, 병렬로
│ 쓰기·셸·네트워크는 Gate01 을 거쳐서만             │
│ 못 한 것 = "놓친 것" (모호 · 인자 부족 · 실패 · 추론 필요)
└──────────────┬──────────────────────────────────┘
               │ 놓친 것들
               ▼
┌────────────── Sequencer (시퀀싱) ───────────────┐
│ 놓친 것 -> 작업 명세(TaskSpec) -> 멱등키 -> 중복 제거 │
│ 의존 순서로 줄 세움 -> NEXT_RAISED (원장)           │
│ 한 번에 하나씩 사고부로                            │
└──────────────┬──────────────────────────────────┘
               ▼
┌────────────── Thinker (사고부, ReAct) ───────────┐
│ RAG 조회 -> Observe -> Plan -> Validate -> Act -> Observe -> Verify
│      Gemini(function calling)  │  Executor(sandbox)  │  코드 verifier
│ 루프 탐지기 · 예산 -> continue / recover / block / terminate
└──────────────┬──────────────────────────────────┘
               ▼
        Gate01 (§5) ──TRUE──> DONE + RAG/Graph 기록 -> 다음 NEXT
               └─RED_RED──> RED_RED_STOP (다음 작업 안 보냄)

가로지르는 층:  Event Ledger(구조화 사건, 항상) · Diagnostic Sink(원시 stdout/stderr, 마스킹)
               Tool Registry(해시 바인딩) · MCP Client(버전 3종 기록)
사용자에게 보이는 글 = Event Ledger 에서 **렌더러가** 그린다. 모델 글은 그 안의 한 칸일 뿐이다.
```

### 2.1 Controller -- 가능한 한 빨리, greedy 하게

- 주문을 **LLM 없이** 먼저 도구에 맞춘다. 이미 있는 길: `walp_se_tool`(`walp/se_tools.py` 카탈로그,
  "확실하지 않으면 실행하지 않고 되묻는다"). 확실도는 매처가 내는 점수이고 문턱은 설정에 박는다.
- 확실한 것 가운데 **부작용이 읽기·계산인 것은 즉시, 의존이 없으면 병렬로** 돈다. 이것이 greedy 의 뜻이다:
  계획을 다 세우고 시작하지 않는다.
- 쓰기·셸·네트워크는 확실해도 바로 안 돈다 -- Gate01 과 컨테이너 검증(C)을 지나야 한다.
- 제어부는 **판단하지 않는다.** 맞추지 못한 것, 인자가 모자란 것, 돌다 실패한 것은 고치려 들지 않고
  그대로 "놓친 것" 으로 넘긴다. 실패를 제어부에서 재시도하면 같은 실패가 두 층에서 두 번 센다.

### 2.2 Sequencer -- 놓친 것을 줄 세운다

- 놓친 것 하나 = `TaskSpec{goal, inputs, allowed_tools, precondition A, postcondition B, alt B', followup, budget}`.
  A·B 는 **실행 가능한 술어 이름**(§5)이다. 비어 있으면 명세 검증에서 거절된다.
- 작업 ID = 실행 ID + 순번. 멱등키 = `sha256(정규화된 TaskSpec + 입력 해시 + 레지스트리 해시)`.
  같은 키가 원장에 `DONE` 이나 `IN_FLIGHT` 로 있으면 다시 안 보낸다(H "중복 이벤트").
- 의존(앞 작업의 산출물을 입력으로 쓰는가)으로 위상정렬. 막힌(BLOCKED) 작업은 **조용히 건너뛰지 않고**
  그것에 의존하는 작업까지 `BLOCKED(upstream=<id>)` 로 원장에 적는다.

### 2.3 Thinker -- ReAct 로 문제를 푼다

한 바퀴(I):

1. **Observe** -- 원장의 최신 상태 + RAG 조회 결과(신뢰 안 함 표지를 달아 넣는다).
2. **Plan** -- Gemini 가 다음 행동을 *제안*한다. 출력은 function call 하나 또는 최종 답 하나.
3. **Validate** -- 도구가 허용 목록에 있나 · 인자가 스키마에 맞나 · 권한(toolgate) · 예산 · 같은 (도구,인자)를 또 부르나.
4. **Act** -- Executor 가 sandbox 에서 돌린다. 모델은 실행하지 않는다.
5. **Observe** -- 끝값 · 구조화 결과 · (원시 로그는 Diagnostic Sink 로).
6. **Verify** -- 사후조건 B 를 **코드가** 검사. 루프 탐지기 평가. 다음 중 하나를 **명시적으로** 고른다:
   continue · recover · block · terminate.

예산: 바퀴 · 재시도 · 벽시계 · 모델 호출 수. 이미 있는 `walp/loop.Budget`/`Supervisor` 의 꼴을 그대로 쓴다
(budget_tools · budget_turns · per_turn · stalled). 넘치면 `LOOP_LIMIT_REACHED` 또는 `FAILED(budget)`.

"가장 완성된 결과" 는 모델의 자평이 아니라 **사후조건을 통과한 결과 중 마지막 것**이다. 통과한 것이 없으면
결과가 없다고 말한다(`NEEDS_REVIEW` 또는 `FAILED`).

### 2.4 RAG / Graph -- 능동적으로 적고, 대조해서 꺼낸다

- 저장소: 이미 있는 `graph/`(append-only 원장: 깃발 · 요약 · 출처 · **원본 해시**, `graph/verify.py` 대조).
  새로 짓지 않는다.
- 외부 정보(웹 · MCP 도구 결과)는 `{출처 URL/서버, 받은 때, 내용 해시, 확인수준}` 과 함께 적는다.
  확인수준은 `paper/출처.jsonl` 의 어휘(전문 · 초록 · 목록 · 조각)를 그대로 쓴다.
- 사고부가 끝낸 작업은 `{작업 ID, 목표, 쓴 도구와 해시, 사후조건 결과, 근거 사건 ID}` 로 적는다.
  **실패도 적는다**(다음 번에 같은 길로 안 가게 -- 부정 결과를 지우지 않는다).
- 꺼낼 때는 해시를 다시 대조하고, 어긋나면 "원본이 그때와 다르다" 를 관측에 같이 넣는다.
- RAG 에서 나온 글은 **데이터지 지시가 아니다**(D.7 과 같은 이유). 프롬프트에서 따로 감싸고, 그 안의 지시문은 따르지 않는다.

## 3. 세 가지 성질을 어디서 얻나

### 3.1 Robustness -- 저장소의 도구를 Gemini 에 맞게 바꾼다

- **목록은 손으로 안 적는다.** `walp/se_tools.py` 가 이미 `bot_tools.py` 의 `@tool` 49개와 `dispatch.py`
  고정 명령을 AST 로 뽑고 부작용(읽기·계산·쓰기·셸·네트워크)과 LLM 사용을 가른다. 그 카탈로그를
  **Gemini `functionDeclarations` 로 옮기는 어댑터**를 더한다.
- 어댑터는 모든 스키마를 **Gemini 가 받는 부분집합**으로 정규화하고, 못 옮기는 도구는 조용히 빼지 않고
  `REJECTED(schema:<사유>)` 로 원장에 남긴다(D.3). 무엇이 부분집합인지는 **flash-lite 실호출 탐침으로 잰다**
  -- 기억으로 정하지 않는다(§9).
- 한 바퀴에 보여 줄 도구 수는 상한을 둔다(주문과 관련된 것만 RAG 로 골라). 작은 모델은 도구가 많을수록
  고르기를 틀린다는 것은 **가설**이고, 상한 값은 §7 Phase 3 에서 쓸기로 정한다.
- 지금 `orchestrator/gemini_http.py` 는 **글만 보내고 글만 받는다**(function calling 없음). function call
  응답(`functionCall` 부분)을 읽는 길을 같은 파일에 더한다 -- 두 벌을 두지 않는다(그 파일의 규율).

### 3.2 Reliability -- 기존 MCP 도구와 능동적으로 맞물린다

- MCP 클라이언트(안쪽): `walp/docs/MCP.md` 가 설계만 해 두고 안 지은 자리다. 여기서 짓는다.
- `initialize` 응답에서 **서버가 실제로 말한 값을 따로** 적는다(A.4):
  `mcp.protocol_version`(협상된 값) · `mcp.server.name/version`(serverInfo) · `mcp.sdk_version`(쓰는 라이브러리,
  표준 라이브러리면 `"none"`). 응답에 없으면 `"unreported"` -- **지어내지 않는다**(A.5).
- `tools/list` 의 각 도구를 같은 어댑터로 넣고, 스키마의 해시로 묶는다. 다음 연결에서 해시가 바뀌면
  그 도구는 재검증 전까지 격리된다(D.6).
- 도구 결과는 언제나 신뢰하지 않는 데이터다(D.7).

### 3.3 Resilience -- 에러가 나거나 코드가 고장났을 때

실패를 먼저 **분류**한다. 분류는 코드가 한다(끝값 · 예외 형태 · HTTP 상태). 이미 있는 분류를 쓴다:
`llm_pool._is_quota / _is_rpm / _is_permanent`.

| 꼴 | 대응 | 같은 게이트를 지나나 |
|---|---|---|
| 일시(429·503·끊김) | 같은 모델, 키만 돌려 재시도. 예산 안에서 | 예 |
| 영구(404·403) | 그 후보 제외. 남은 후보 없으면 `BLOCKED(provider)` | -- |
| 스키마(인자 불일치) | 모델에 오류를 관측으로 돌려 한 번 더. 같은 오류 2회면 루프 탐지기에 넘김 | 예 |
| 도구 코드 고장(예외·끝값≠0 재현) | 회로 차단(그 도구 격리) + 이미 있는 `repair/`(sandbox 재현 → 패치 제안 → sandbox 검증) | 예 -- 고친 도구는 새 해시로 **재등록 시험부터** |
| 사후조건 실패 | Gate01 의 대체 경로(§5) | 예 |

복구 시도는 원래 행동과 **같은 게이트를 지난다**(I). 복구 경로가 게이트를 우회하는 길은 없다.

## 4. Event Ledger 와 사용자 출력

- 사건 한 줄: `{run_id, task_id, seq, ts, type, actor(code|model|executor), data, evidence:[event_id…]}`.
  `type` 은 닫힌 목록(NEXT_RAISED · GATE_EVAL · NEXT_DISPATCHED · TOOL_START · TOOL_END · LOOP_EVAL ·
  TERMINAL · LOG_SINK_FAIL …).
- 원시 stdout/stderr 는 `Diagnostic Sink` 파일로만(E.1·E.2). 쓰기 전에 `secret_filter.py` 로 마스킹(E.5).
- **로그 쓰기가 실패하면 그 실행은 `LOGGING_FAILURE` 로 끝난다**(E.4). 원장이 없는 진행은 검사할 수 없는 진행이다.
- 사용자에게 가는 글은 렌더러가 원장에서 그린다: 한 일 · 판정 · 근거 요약 · 결과(E.7). 모델의 최종 답은 그중
  한 칸이고, **그 칸 안에 깃발 낱말이 있으면 위조로 본다**(§5 H0).
- 원장 위치는 `ledgerroot.py` 의 `SE_LEDGER_ROOT` 를 따른다 -- 시험은 임시 자리에 쓴다(CLAUDE.md '검사는 재는 것').

## 5. 게이트 -- 깃발은 여기서만 나온다

### H0. 깃발 위조 게이트 (새로, 가장 먼저 짓는다)

모델 출력에서 깃발 어휘(`*_DETECTED` · `RED_RED_STOP` · `A_TO_B` · `DONE` 등 §J 전부 · `version` 주장)를 찾으면:
그 답은 채택하지 않고 `MODEL_FLAG_FORGERY` 사건을 남긴 뒤 같은 바퀴를 한 번 다시 묻는다(재시도도 예산에서).
**글자 검사의 한계를 안다** -- 바꿔 말한 위조("루프는 없었습니다")는 못 잡는다. 그래서 H0 은 첫 번째 벽이고,
두 번째 벽은 **렌더러가 모델 글을 상태 칸에 절대 안 넣는 것**이다. 상태 칸은 원장에서만 채워진다.

### Gate01 을 실행 가능하게 만든다

정책 G 는 A_TO_B 를 평가하라고 하지만 A 와 B 가 무엇인지 말하지 않는다 -- 그래서 모델이 채웠다.
여기서는 **TaskSpec 이 술어를 함수로 들고 온다**:

```
A_TO_B          = primary action 이 실행됨  AND  postcondition B(state) 가 코드 검사로 참
NOT_A_TO_B_PRIME = TaskSpec.alt 가 정의돼 있음 AND alt action 이 실행됨 AND B'(state) 가 참
NOT_B_PRIME 후속 = TaskSpec.followup (정의돼 있어야 함) -> 실행 -> 사후조건 검사
```

판정은 세 값이다: `TRUE · FALSE · UNKNOWN`. **UNKNOWN 은 FALSE 로 다룬다**(G: "없는 결과를 TRUE 로 읽지 마라").
alt 나 followup 이 정의되지 않았으면 그 단계는 실행되지 않은 것이고, 실행되지 않은 것은 FALSE 다
→ 그 경로는 `RED_RED_STOP` 으로 간다.

```
eval A_TO_B
 ├ TRUE  -> 나머지 필수 게이트(gatekeeper · toolgate · 컨테이너 검증) 전부 -> 통과면 승인 ID -> 다음
 └ FALSE/UNKNOWN -> eval NOT_A_TO_B_PRIME
       ├ FALSE/UNKNOWN -> RED_RED_STOP (사슬 정지, 다음 작업 안 보냄)
       └ TRUE -> followup 실행 -> 사후조건
              ├ 통과 + 필수 게이트 통과 -> 승인
              └ 실패 -> FAILED(followup) (다음 작업 안 보냄)
```

### 루프 탐지기

상태 지문 = `hash(task_id, 정규화된 관측 요약, 마지막 (도구, 인자 해시), 마지막 실패 코드)`.
탐지 조건(문턱은 설정): 같은 지문 k 회 · 같은 (도구,인자) k 회 · 같은 실패 코드 k 회 · 새 관측 0 이 m 바퀴.

- 평가했고 걸렸다 → `LOOP_DETECTED` · 평가했고 안 걸렸다 → `NO_LOOP_DETECTED`
- 평가를 못 했다(지문을 못 만듦 · 탐지기 예외) → `UNKNOWN`
- 원장에 `LOOP_EVAL` 사건이 없는 바퀴의 루프 상태는 렌더러가 `UNKNOWN` 으로 그린다. **"로그가 없으니 루프가 없다" 의 길이 코드에 없다.**

### 종료 상태

J 의 일곱 개(DONE · BLOCKED · FAILED · NEEDS_REVIEW · RED_RED_STOP · LOOP_LIMIT_REACHED · LOGGING_FAILURE)
에 사유 코드를 붙인 열거형. TERMINAL 사건 없이 끝난 실행은 렌더러가 `FAILED(no_terminal_event)` 로 그린다.

## 8. 선행조사 -- 아직 짓기 전이다

**이 구조는 새롭지 않다.** 제어부(greedy 실행) · 시퀀싱(못한 것을 줄 세움) · 사고부(ReAct 로 다시 계획)는
아래와 아주 가깝다. 이 세션에서 **원문을 읽지 않았다** -- 전부 기억이고 `[출처:기억]` 이다. 짓기 전에 읽어야 한다.

| 무엇 | 어디(기억) | 가까운 점 |
|---|---|---|
| ReAct | Yao et al., 2022, arXiv:2210.03629 `[출처:기억]` | 사고부의 Observe→Act 고리 그 자체 |
| LLMCompiler | Kim et al., 2023, arXiv:2312.04511 `[출처:기억]` | **가장 가깝다.** 플래너 + 의존이 풀린 함수 호출을 즉시 병렬로 보내는 단위 + 결과를 보고 다시 계획하는 단위. 우리 Controller/Sequencer/Thinker 와 거의 대응 |
| Reflexion | Shinn et al., 2023, arXiv:2303.11366 `[출처:기억]` | 실패를 기억에 적고 다음 시도에 쓰는 것(§2.4 의 실패 기록) |
| GraphRAG | Microsoft, 2024, arXiv:2404.16130 `[출처:기억]` | 그래프 꼴 RAG |

**우리가 다른 점(주장이 아니라 설계 의도):** 구조가 아니라 **판정의 소재**다. 위 것들은 진행 상태를 모델의 출력에서
읽는다. 여기서는 상태 · 버전 · 게이트 판정을 모델 어휘 밖에 두고 원장에서만 그린다. 이것조차 기존 "LLM-as-tool,
code-as-judge" 계열 작업에 이미 있을 가능성이 높다 -- **아직 못 본 곳:** 가드레일 프레임워크(NeMo Guardrails 등),
에이전트 감사 로그 연구, Gemini 공식 function calling 문서의 스키마 제한. 그래서 이것을 기여라고 부르지 않는다.
이 저장소가 필요로 하는 것은 새로움이 아니라 **지금 답이 거짓 깃발을 내지 않는 것**이다.

  모음에서 60 문장 중 9~10 개(사전등록 안전 기준 5% 를 못 넘었다). 여기서 손으로 넣어 본 "고마워요 이제 머지해줘" 도
  삼켜졌고, 시험이 그 사실을 고정해 둔다. 그래서 화면이 매번 `'//'` 로 건너뛰는 법을 같이 보인다.
- 이 대화에서 사용자가 실제로 보낸 말 다섯은 전부 모델로 넘어갔다(시험에 그대로 있다). **다섯은 표본이 아니다** --
  잡담 판정의 오류율을 말하려면 봉인 모음으로 재야 한다.
- Claude Code 훅(`walp-front install-hook`)은 **걸지 않았다.** 앞단은 agentic 의 Gemini 경로 앞에만 섰다.

## 13. 3단계 -- 도구 생성·검증·등록 · 제어부

```
주문 -> WALP 앞단 -> 제어부(agentic/controller.py)
                       walp/se_router.route (LLM 없음)
                       ├ 등록된 도구 + 인자가 선언에 맞음 + 원문 해시 같음
                       │     -> 작업 하나짜리 Gate01 사슬 -> 승인이면 도구 출력이 답(신뢰 안 함 표시), 모델 0
                       │     -> 게이트에서 지면 그 상태로 끝(모델로 안 간다)
                       └ 그 밖(ASK · REJECT · 미등록 · 인자 틀림 · 원문 바뀜) -> 놓친 것 -> 모델
```

| 파일 | 하는 일 |
|---|---|
| `agentic/tools.py` | 카탈로그 -> Gemini `functionDeclarations`(STRING · INTEGER · NUMBER · BOOLEAN). 거절 사유를 도구마다 남긴다. 입력·출력 스키마 검사 |
| `agentic/tool_probes.json` | **사람이 적은** 탐침(인자 · 기대 글자). 없으면 `no_probe` |
| `agentic/tool_registry.json` | `--register` 의 결과(커밋한다). 선언 해시 · 함수 원문 해시 · 등록 때 HEAD |
| `agentic/controller.py` | 위 그림 |

**등록 결과(d13f878, 진짜 sandbox):** 등록 5 -- `read_file` · `spice_example` · `concept` · `search_memory` · `textbook`.
거절 64(첫 사유 기준): Gemini 이름 규칙 20(`cmd:!…` dispatch 명령) · 탐침 없음 18 · 권한 밖 11(셸·쓰기·네트워크) ·
인자 이름 9(한글 인자) · LLM 사용 6. 카탈로그의 분류가 추정이라 **탐침을 적은 것만** 등록된다 -- 예: `orchestrator_solve`
는 '계산' 으로 분류되지만 실제로는 백그라운드 런을 띄우고 그 런이 LLM 을 부른다. 그래서 탐침을 일부러 안 적었다.

**도구를 고치면:** 그 함수 원문 해시가 바뀌어 제어부가 그 도구를 격리한다(`quarantined:source_changed` -> 모델로).
`python3 -m agentic.tools --register` 를 **커밋한 뒤에** 다시 돌리고 등록부를 커밋한다(sandbox 는 HEAD 를 본다).
`tests/test_agentic_phase3.py` 가 등록부와 지금 나무가 어긋나면 빨개진다.

**알게 된 것:** LLM 없는 라우터가 "CTLE 가 뭐야" 를 `serdes_link`(BER 시뮬레이터)로 보낸다. 미등록이라 모델로 넘어갔지만,
등록돼 있었다면 엉뚱한 도구가 돌았을 것이다. 등록을 넓힐수록 라우터의 오분류가 그대로 실행이 된다 -- 넓히기 전에 라우터를 잰다.

**한계:** 원문 해시는 `bot_tools.py` 의 그 함수 몸통만 본다(부르는 모듈이 바뀌어도 같다). Gemini 이름 규칙과 스키마 꼴은
기억으로 적었고 실호출로 확인하지 않았다. 선언은 만들었지만 **Gemini 가 그 선언으로 도구를 부르는 길(function calling)은
아직 없다** -- 4단계 사고부에서 쓴다.
