# 정책을 하드웨어에 올리기 — bare-metal C 인가 OS 가 필요한가 (NASA AOS/cFS/OSAL 기준)

사용자 물음: 실제 하드웨어엔 LLM 이 없다. Mamba 를 "LLM"으로 돌리면 무겁다. **Mamba+SSM 은
bare-metal 에서 C 로만 되는가, OS 가 필요한가?** 그리고 **각 정책을 HW 에 어떻게 올리나?**

## 결론부터 — 추론 커널은 bare-metal C 로 된다 (실측 증거 있음)

작은 selective-SSM 추론은 **LLM 이 아니다.** 한 스텝이
`입력투영(MAC) → Δ,B,C 투영(MAC) → Ā=exp(Δ·A)(초월함수 1개) → 상태갱신 스캔(MAC) → 출력(MAC)`
의 **고정 데이터플로**다. 동적 메모리·재귀·가변 길이가 없다.

**증거(주장 아님)**: `ssm/fw/ssm.c` 가 바로 그 커널이고 — **힙 없음·재귀 없음·경계 있는 루프·
결정적(MCU 안전)** — `make && ./host_test` 가 방금 **ALL PASS**:
```
[decay] 0 입력 → ||h||² 단조 감쇠 (IIR 확인)
[stable] 상수 입력 300스텝 → ||h||²=4.289 유계
[valhead] value() 순수·결정적, advance() 전진
[wire] lambda=0==la2, lambda>0 유효, RTA 무조건 적용
```
→ **추론 커널에는 OS 가 필요 없다.** 유일한 특수 연산 exp 는 고정소수서 **LUT**(=`ssm/rtl/exp_unit.v`,
측정됨: 순수 로직, DSP 0)로 바꾼다. 스캔 MAC 은 `ssm/rtl/scan_mac.v`(DSP)로 간다. 학습은
오프디바이스(GPU/numpy), **추론만 MCU/FPGA**.

## 그럼 OS/RTOS 는 어디에 필요한가

커널이 아니라 **주변 배선**이다: 다중 센서 드라이버·ISP/DSP(카메라·LiDAR·열)·IPC·로깅·
임무계획·fault 관리. 이것은 NASA 방식(AOS→cFS→OSAL→RTOS)의 계층 그대로다. 즉 UAV 전체를
한 OS 에 올리지 않고, **요구에 따라 층을 나눈다**:

```
비행제어(하드 1kHz)         임무컴퓨터(연성 실시간)
  RTOS/bare-metal            Linux/RTOS + cFS/OSAL(app)
  IMU→자세추정→제어→모터      센서 드라이버·ISP·perception·센서정책·탐색계획
       ↑ 결정적 마감              ↑ 여기서 정책 커널을 부른다(OS 는 배선용, 커널은 OS-free)
```
비행 안정화와 센서-선택 정책이 분리된다(NASA ICAROUS-2 의 safety-critical core ↔ mission SW 분리, publish/subscribe).

## 각 정책을 HW 에 올리는 법 (구체화)

| 정책 | 계산량 | HW 배치 | OS 필요? | 근거 |
|---|---|---|---|---|
| **NASA-rule 효용** (U_i=ΔP−α·cost) | MAC 몇 개 + 비교 | MCU bare-metal C | 아니오 | 자명. 임무컴퓨터/비행컴퓨터 어디든 |
| **Mamba selector** (selective-SSM) | 고정 MAC + exp-LUT + 스캔 | `ssm/fw/ssm.c`(bare-metal) → 옵션 FPGA(scan_mac DSP+exp_unit LUT) | **커널 아니오** (배선만 OS) | host_test ALL PASS·힙없음·결정적 |
| **policy_core value head(②)** | 결정적 belief + SSM value-to-go + RTA | `ssm/fw/ssm_value.c`(PC_ValueHead) + policy_core C | 아니오 | 코어는 SSM 모름(함수포인터). RTA 무조건 최후 |

- **학습된 가중치 이식**: selector_train 이 낸 가중치를 `SSM_Weights` const 배열로 export →
  `ssm/fw/ssm.c` 가 그대로 추론. (numpy selector ↔ ssm.c 구조 브리지는 다음 단계 — 커널 자체는 증명됨.)
- **자원·지연은 잰다**: ssm/ 가 exp LUT·scan DSP 를 이미 쟀다. value head 를 올리면 그 자원으로
  end-to-end 스텝 지연을 STA 로 잰다(주장 말고 측정 — ssm/설계 규율).

## 검증(sar)과의 관계

`sar/` 는 절대 레퍼런스(심판)다. 어느 정책이든 sar reference·evaluator 로 채점한다. 실측 비교
(태백산 학습 → 지리산 검증, held-out): **NASA-rule 71% > Selector(Mamba) 54% > Baseline 38%**
(탐지율). 2센서 결정은 대체로 가시도 함수라 학습 Selector 가 NASA 규칙을 아직 못 이겼다 —
정직한 현재 결과. HW 채택은 이 비교가 가리키는 정책으로 한다(지금은 NASA-rule 이 앞선다).

## 정직 (한계)

- `ssm/fw/ssm.c` 는 **float 참조 구현**이다. 고정소수(Q15/Q4.12)+LUT 이식은 명시된 다음 단계(README).
- value head 학습 가중치는 아직 없다 → `ssm_value.c` 의 lambda=0(안 잰 이득 안 켠다, 과장방지).
- 지연·자원 수는 STA/합성으로 재기 전엔 주장 아님. NASA 인용은 문서지도(NTRS ID) — 원문 전문 미열람 [출처:조각].
